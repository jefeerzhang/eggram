# 画面设计：按知识关系选择形式

此文规定微课的画面设计，不替代阶段 0 的用户确认。字段权威表见 [json-schema.md](json-schema.md)，时间规则见 [motion.md](motion.md)。

## 先判断画面在解释什么

`kind` 表示教学角色，`layout_variant` 表示画面形式，`style` 只表示皮肤。换皮、加图标、推拉文字，都不能替代知识关系的可视化。

| 要解释的内容 | 选用 | 学习者看见什么 |
| --- | --- | --- |
| 一个概念由哪些部件构成 | `rule` + `structure` | 根节点连到 2–4 个部件，逐项点亮 |
| 动作怎样改变对象 | `example` + `steps` | 2–4 步的动作、对象、结果；按顺序点亮 |
| 哪里错、怎样改、为何改 | `mistake` + `compare` | 1–3 行错误对照；先见错误，再见修正与原因 |
| 数学关系及符号含义 | `rule` + `formula` | 主式及分项，见 [formulas.md](formulas.md) |
| 数值随自变量变化 | `diagram` + `chart` | 曲线、坐标与标注 |
| 句子判别、定义、短口诀 | 默认版式或 `side` | 聚焦短文本，不为装饰硬画关系 |

边界：`structure` 是一层分解图，不是任意网络；`steps` 是示意操作台，不是录屏、可点击软件或真实 API 执行；`compare` 是教学对照，不是自动生成答案。真实界面截图、嵌套关系、自定义路径不在这三个变体内。

## 阶段 0：交付画面计划

逐页大纲增加「画面形式与变化」列。每页说明：

1. 学习者看什么对象。
2. 对象之间有什么关系，或动作产生什么结果。
3. 哪些内容先出现，哪些内容后出现。

讲解段优先使用至少两种适合知识点的画面形式。连续超过两页沿用同一种形式时，检查是否只是重复文字卡片。保留相同形式也可以，但须在大纲里说明教学理由。不要为满足数量把一句定义拆成伪流程；此项是人工设计检查，不是 JSON 硬闸门。

例如，「Agent 能力组成」适合用根节点与部件；「查时段→创建日程」适合展示操作对象与结果；「知识与执行混淆」适合错误对照。对经济学主题可替换成「决策因素→预算约束」「查看价格→计算总成本」「沉没成本→未来成本」；字段无需绑定学科。

## 阶段 1：落入结构化内容

从确认的画面计划生成 `visual`，不是把全部正文复制到卡片。`body` 保留一句结论。数组顺序同时决定读图与点亮顺序。字段示例、数量及长度上限见 [json-schema.md](json-schema.md#visual-对象结构操作纠错)。

- `structure`：`label` 是根节点；每项 `label` 是部件名，`text` 是部件作用。
- `steps`：每项 `label` 是动作，`text` 是操作对象或输入，`result` 是该步结果。不得只写三段泛泛描述冒充操作。
- `compare`：每项 `wrong` 用 `**` 标错误，`right` 写修正，`reason` 写原因。无需把整行染红或把原因塞进标题。

全局和每页关闭 motion 时，所有内容静态完整展示。预览使用完整末态，因此能检查全部内容的溢出。开启 motion 时，顺序按旁白总时长均分；不是逐句或逐词对齐。旁白讲述顺序须与数组一致。若某步讲得很久，调整页面拆分，不得声称系统已实现语音标记对齐。

## 验收

- 闸门：结构数据完整；未知字段、错用变体、超出数量/长度、缺失纠错高亮均报错。
- 预览：全部节点、对象、结果和原因可见，无溢出。超量文本应拆页，不自动裁字。
- 成片：点亮顺序与讲述顺序一致；关闭 motion 后不隐藏答案或结果。
- 设计：相邻页切换了信息表达方式，而不是只换背景、徽标或颜色。

不要为了验证通用能力改写现有课件。模板测试使用独立测试数据；实际新课仍须通过阶段 0。
